## Conventions

- Python 3.12+, standard library only (sqlite3, decimal, http.server, unittest, ...). The package is `wms/`, run as `python3 -m wms [--db PATH] [--json] [--user NAME] [--now TIME] COMMAND ...`. Global options come before the command. `--db` defaults to `wms.db` in the current directory.
- `--now` sets the current time for the command, as `YYYY-MM-DDTHH:MM:SSZ` (UTC); without it, the real current time. Every time the system stores or prints is UTC in that format. "Today" is the date part of the current time. Dates are `YYYY-MM-DD`.
- With `--json`, a successful command prints exactly one JSON document on stdout, in the shapes below; without it, any readable text. Exit code 0.
- A user error (bad input, a broken rule, an unknown object, a missing permission) prints a message starting with `error: ` on stderr, nothing on stdout, exits with code 2, and changes nothing at all: every command is all-or-nothing.
- Every command except `init` needs `--user NAME`, naming an existing, enabled user whose role allows the command (section 1). Otherwise it is a user error.
- Quantities follow the product's unit: `each` takes whole numbers, `kg` up to 3 decimals. More decimals, a non-number, or zero or less where a quantity is needed is a user error. Quantities print as strings: `each` as an integer (`"12"`), `kg` with exactly 3 decimals (`"1.250"`).
- Money is in the book's currency. Amounts print as strings with exactly 2 decimals (`"12.30"`); unit costs and unit prices are accepted with up to 4 decimals and print with exactly 4 (`"1.2500"`). Never use binary floating point for money or quantities. All rounding is half up: round2 rounds to 2 decimals, round4 to 4.
- Lists in JSON output are sorted as stated; where nothing is stated, by id or code, ascending.
- Ids are assigned in order of creation: movements are integers from 1; documents are `PO-0001`, `SO-0001`, `TR-0001` and `RT-0001`, with a separate counter per kind.

## 1. Setup and users

- `init --currency CUR --admin NAME` creates the book. CUR is 3 uppercase letters; NAME becomes the first user, with role `admin`. A second `init` on the same database is a user error. `init` needs no `--user`.
- User names are 1 to 32 characters from `a-z`, `0-9`, `.`, `_` and `-`. Roles, from least to most: `viewer`, `clerk`, `manager`, `admin`. Each role may do everything the roles below it may:
  - viewer: every command that only reads (lists, shows, reports).
  - clerk: `receive`, `move`, `adjust`, `scrap`, `po receive`, `so pick`, `so ship`, `transfer create`, `transfer receive`.
  - manager: `product add`, `product edit`, `import products`, `warehouse add`, `location add`, `customer add`, `price set`, `promo add`, `po create`, `po close`, `so create`, `so confirm`, `so allocate`, `so cancel`, `transfer cancel`, `return create`, `movement void`.
  - admin: `user add`, `user role`, `user disable`.
- `user add NAME --role ROLE`; `user role NAME ROLE` changes a role; `user disable NAME`. `user list` → `[{"name": "alice", "role": "admin", "enabled": true}, ...]`, sorted by name. A duplicate name, an unknown role, or an unknown user is a user error. Lowering the role of, or disabling, the last enabled admin is a user error.

## 2. Products

- `product add SKU --name TEXT [--unit each|kg] [--tracking none|lot|serial] [--costing fifo|average] [--min QTY] [--max QTY]`. Defaults: `each`, `none`, `fifo`, no minimum, no maximum. A SKU is 3 to 20 characters from `A-Z`, `0-9` and `-`, starts with a letter, and is unique. `serial` tracking needs unit `each`. The name is 1 to 100 characters once surrounding spaces are removed (they are). When both are given, max must be at least min.
- `product show SKU` → `{"sku": "BOLT-M8", "name": "Bolt M8", "unit": "each", "tracking": "none", "costing": "fifo", "min": "100", "max": "500", "version": 1}`; `min` and `max` are null when unset.
- `product list [--search TEXT]` → a list of those objects, sorted by SKU. `--search` keeps products whose SKU or name contains TEXT, ignoring case.
- `product edit SKU --version N [--name TEXT] [--min QTY|none] [--max QTY|none]`. N must equal the product's current version, otherwise it is a user error (someone changed the product in between). A successful edit adds 1 to the version. `none` clears the minimum or maximum. The min/max rule above holds after the edit. Unit, tracking and costing never change.

## 3. Warehouses and locations

- `warehouse add CODE --name TEXT`. CODE is 2 to 6 characters from `A-Z` and `0-9`, unique. Each new warehouse gets two locations: `RECV` (type `receiving`) and `SHIP` (type `shipping`).
- `location add WH/LOC [--type storage|receiving]` (default `storage`). LOC is 1 to 20 characters from `A-Z`, `0-9` and `-`, unique within its warehouse. Everywhere, a location is written `WH/LOC`.
- `warehouse list` → `[{"code": "WH1", "name": "Main"}, ...]`. `location list WH` → `[{"location": "WH1/A-01", "type": "storage"}, ...]`, sorted by location.

## 4. Stock and movements

Stock is held per product, location, and lot (for lot-tracked products) or serial number (for serial-tracked products, one unit each); untracked products have no lot. Stock is never below zero anywhere. Every change of stock is a movement:

`{"id": 1, "at": "2026-03-02T09:00:00Z", "user": "carol", "type": "receive", "sku": "BOLT-M8", "qty": "100", "from": null, "to": "WH1/RECV", "lot": null, "serials": [], "unit_cost": "0.1200", "value": "12.00", "ref": null}`

`type` is one of `receive`, `move`, `adjust`, `scrap`, `pick`, `ship`, `transfer-out`, `transfer-in`, `return`, `void`. `from` or `to` is null when stock comes from or goes outside the book. `unit_cost` is set on `receive` and `return` movements and null on others. `value` is the stock value the movement brought in or took out (section 5); it is `"0.00"` for movements inside a warehouse (`move`, `pick`). `ref` names the document or movement a movement belongs to.

- `receive SKU QTY --at WH/LOC --cost UNITCOST [--lot LOT --expires DATE] [--serial S1,S2,...]` brings stock in from outside into a `receiving` or `storage` location. UNITCOST is 0 or more. Lot-tracked products need `--lot` (1 to 30 characters from `A-Z`, `0-9` and `-`) and `--expires`; a lot already received keeps its expiry, and a different `--expires` for it is a user error. Serial-tracked products need `--serial` with exactly QTY distinct serials (1 to 30 characters from `A-Z`, `0-9` and `-`), none of them in stock anywhere already. Untracked products take neither option. → the movement.
- `move SKU QTY --from WH/LOC --to WH/LOC [--lot LOT] [--serial S1,...]` moves stock between two different locations of the same warehouse; the destination can't be the `SHIP` location (stock gets there only by `so pick`). Only unreserved stock can move (section 8). Lot-tracked products need `--lot`; serial-tracked products need `--serial` with exactly QTY serials, all at the source location. → the movement.
- `adjust SKU --at WH/LOC --count QTY --reason TEXT [--lot LOT]` records a stock count: the product's stock at that location (and lot) becomes QTY (0 or more). The difference is an `adjust` movement: an increase comes `from` null, a decrease goes `to` null; no difference is a user error. A count below what is reserved there is a user error. Lot-tracked products need `--lot`, and an increase needs a lot that has been received before; serial-tracked products can't be adjusted. → the movement.
- `scrap SKU QTY --at WH/LOC --reason TEXT [--lot LOT] [--serial S1,...]` takes unreserved stock out of the book (`to` null). → the movement.
- `movement list [--sku SKU] [--warehouse WH] [--type TYPE] [--since TIME] [--until TIME]` → movements, oldest first. `--warehouse` keeps movements whose `from` or `to` is in that warehouse; `--since` and `--until` are inclusive.
- `movement void ID --reason TEXT` records a `void` movement that exactly reverses movement ID: `from` and `to` swapped, the same SKU, qty, lot, serials and value, `ref` `"MV-ID"` (for example `"MV-7"`). Only `receive`, `move`, `adjust` and `scrap` movements can be voided, each only once; voiding a `void` is a user error. The reversal may not leave stock below zero or below what is reserved. Voiding a receipt, or an increasing adjust, takes its cost layer out again (section 5); for `fifo` products that is a user error once any of that layer has been consumed, and for `average` products once there has been any later movement of the product into or out of that warehouse. Voiding a decrease (a decreasing adjust or a scrap) puts back exactly the value it took out; for `fifo` products, into the very layers it consumed. → the void movement.

## 5. Costing

Each product is costed per warehouse, by its costing method. Stock in a `SHIP` location is still in the warehouse's stock; stock in transit (section 9) is in neither warehouse's.

- `fifo`: each `receive`, increasing `adjust` and `return` creates a cost layer in the warehouse: `{movement id, time, qty, unit cost}`. Stock leaving the warehouse (`ship`, `scrap`, a decreasing `adjust`, `transfer-out`) consumes the remaining quantity of the layers oldest first (by time, then by movement id), whatever the location or lot the units come from. Its value is round2 of the sum, over the consumed slices, of slice quantity × layer unit cost. An increasing adjust gets the unit cost of the newest layer the product ever had in that warehouse (consumed or not); with no layer ever, the adjust is a user error. A receipt's value is round2(qty × unit cost); so is an adjust's or a return's. The value of a warehouse's stock of a product is round2 of the sum of remaining quantity × unit cost over its layers.
- `average`: the warehouse keeps the product's quantity Q and value V (2 decimals). A receipt (or return) of q at unit cost c adds round2(q × c) to V and q to Q. The average cost A is round4(V / Q) whenever Q > 0. Stock leaving: taking out q with q < Q is valued round2(q × A); taking out all of Q is valued V. An increasing adjust of q is valued round2(q × A), with A the warehouse's average right before, or the last average it had when Q is 0; it adds that value to V. With no average ever, the adjust is a user error. The value of the warehouse's stock is V.
- `valuation [--warehouse WH] [--at TIME]` → `{"rows": [{"sku": "BOLT-M8", "warehouse": "WH1", "qty": "88", "value": "10.56"}, ...], "in_transit": [{"transfer": "TR-0001", "sku": "...", "qty": "...", "value": "..."}], "total": "..."}`. Rows are the products with stock in a warehouse, sorted by warehouse, then SKU; `in_transit` lists the transfers in transit; `total` adds up the rows and the in-transit values. With `--warehouse`, only that warehouse's rows and the transfers leaving or entering it. `--at` gives the valuation as it stood right after the last movement at or before TIME.
- `aging --warehouse WH [--at DATE]` → `[{"sku": "BOLT-M8", "0-30": "10.56", "31-90": "0.00", "91+": "0.00"}, ...]`, for `fifo` products only: the value (round2 per bucket) of each product's remaining layers in the warehouse, by age in whole days on DATE (default today), age = DATE − the date of the layer's time. Sorted by SKU; products with no remaining layers are left out.

## 6. Purchase orders

- `po create --supplier NAME --warehouse WH --line SKU:QTY:UNITCOST [--line ...]` creates a purchase order with status `open`. → the `po show` object.
- `po receive PO --line N --qty QTY --at WH/LOC [--lot LOT --expires DATE] [--serial S1,...]` receives against line N (1 is the first line) at the line's unit cost, into a location of the PO's warehouse, with the rules of `receive`. It is a `receive` movement with `ref` the PO id. A line's received quantity may exceed its ordered quantity by at most 5% (ordered × 1.05, rounded down to the unit's precision); more is a user error. Receiving on a `received` or `closed` PO is a user error. → the movement.
- `po close PO` closes an `open` or `partial` PO: nothing more can be received. → the `po show` object.
- A PO's status is `closed` once closed; otherwise `received` when every line has received at least its ordered quantity, `partial` when anything has been received, and `open` when nothing has. A line's received quantity counts its receipts, minus those voided (so a void can turn `partial` back into `open`).
- `po show PO` → `{"id": "PO-0001", "supplier": "Acme", "warehouse": "WH1", "status": "partial", "lines": [{"line": 1, "sku": "BOLT-M8", "ordered": "100", "received": "40", "open": "60", "unit_cost": "0.1200"}], "value_received": "4.80"}`. `open` is ordered − received, never below 0, and 0 on a closed PO. `value_received` is the value of the PO's receipts, net of voids.
- `po list [--status S]` → the `po show` objects.

## 7. Customers, prices and promotions

- `customer add NAME [--price-list LIST]` (NAME 1 to 60 characters, unique); `customer list` → `[{"name": "Bistro", "price_list": "TRADE"}, ...]`, `price_list` null when unset.
- `price set LIST SKU UNITPRICE [--min-qty QTY]` sets a unit price in a price list (LIST is 1 to 10 characters from `A-Z` and `0-9`) for line quantities of at least QTY (default 0). Setting the same list, SKU and minimum quantity again replaces the price. `price list [--list LIST]` → `[{"list": "STANDARD", "sku": "BOLT-M8", "min_qty": "0", "unit_price": "0.2500"}, ...]`, sorted by list, SKU, then minimum quantity.
- A line's unit price is the price with the highest minimum quantity at most the line's quantity, from the customer's price list; if that list has no such price for the SKU, from the list `STANDARD`; with neither, confirming the order is a user error.
- `promo add CODE --sku SKU --percent P --from DATE --to DATE` adds a line promotion; `promo add CODE --order --threshold AMOUNT --percent P --from DATE --to DATE` adds an order promotion. CODE is unique, 1 to 20 characters from `A-Z`, `0-9` and `-`; P is more than 0 and at most 100, with up to 2 decimals; the dates are inclusive and from ≤ to. `promo list` → `[{"code": "SPRING", "kind": "line", "sku": "BOLT-M8", "threshold": null, "percent": "10.00", "from": "2026-03-01", "to": "2026-03-31"}, ...]` (`kind` `line` or `order`; `sku` null for order promotions, `threshold` null for line ones).
- Pricing happens when an order is first confirmed, with promotions valid on that day. For each line: `gross` = round2(qty × unit price); `discount` = round2(gross × P / 100) with P the largest percent among the line promotions for its SKU, or 0; `net` = gross − discount. Then `subtotal` = the sum of the nets; `order_discount` = round2(subtotal × P / 100) with P the largest percent among order promotions whose threshold is at most the subtotal, or 0; `total` = subtotal − order_discount. Prices never change after the first confirmation.

## 8. Sales orders and reservations

- `so create --customer NAME --warehouse WH --line SKU:QTY [--line ...]` creates an order with status `draft` and no prices yet. → the `so show` object.
- An order's status is `draft` until it is confirmed and `cancelled` once cancelled; otherwise it is `shipped` when every line is fully shipped, `partially_shipped` when anything has been shipped, `confirmed` when every line's quantity is reserved, picked or shipped, and `backordered` when it isn't.
- `so confirm SO [--hold HOURS]` prices a `draft` order (section 7) and reserves stock for it. Its reservations expire HOURS hours from now (1 to 720, default 48); the order keeps its hold hours. → the `so show` object.
- Reserving takes, for each line in line order, unreserved stock from the order warehouse's `storage` locations only (never `receiving` or `SHIP`), in this order: for lot-tracked products by lot expiry, then lot, then location; for serial-tracked products by location, then serial; for other products by location. Lots that expired before today are never reserved. A line can be reserved across several locations and lots. Available stock is stock in `storage` locations minus what is reserved there.
- `so allocate SO`, for a `confirmed`, `backordered` or `partially_shipped` order, reserves whatever is still neither reserved, picked nor shipped, by the same rules, and sets all its unpicked reservations to expire HOURS (the order's hold) from now. → the `so show` object.
- Whenever any command runs at or after a reservation's expiry time, before anything else that reservation is released, with one audit entry per order whose reservations expired: action `reservation.expire`, target the order id, user `system`. This happens even if the command itself only reads, and even if it later fails as a user error (then it is undone with the rest, and repeats next time).
- `so pick SO` moves all the order's reserved stock to the warehouse's `SHIP` location (`pick` movements, `ref` the order id), one movement per SKU, source location and lot. Picked stock stays the order's and never expires. Nothing reserved is a user error. → `{"order": "SO-0001", "picks": [{"sku": "...", "from": "WH1/A-01", "lot": null, "serials": [], "qty": "..."}, ...]}`, sorted by source location, then SKU, then lot.
- `so ship SO` ships all the order's picked stock: `ship` movements from `WH/SHIP`, `to` null, `ref` the order id, one per line and lot, in line order, valued by section 5. Nothing picked is a user error. → the `so show` object.
- `so cancel SO` cancels an order with nothing shipped: all its reservations are released (picked stock stays in `SHIP`, no longer the order's). Status `cancelled`. → the `so show` object.
- `so show SO` → `{"id": "SO-0001", "customer": "Bistro", "warehouse": "WH1", "status": "confirmed", "hold": 48, "expires": "2026-03-04T09:00:00Z", "lines": [{"line": 1, "sku": "BOLT-M8", "qty": "50", "unit_price": "0.2500", "gross": "12.50", "discount": "1.25", "net": "11.25", "reserved": "50", "picked": "0", "shipped": "0", "returned": "0"}], "subtotal": "11.25", "order_discount": "0.00", "total": "11.25"}`. `reserved` counts reserved but not picked; `picked` counts picked but not shipped. Prices are null before the first confirmation; `expires` is the expiry of the unpicked reservations, or null when there are none. `so list [--status S]` → the `so show` objects.
- `stock [--warehouse WH] [--sku SKU] [--at TIME]` → `[{"sku": "BOLT-M8", "location": "WH1/A-01", "lot": null, "serials": [], "on_hand": "60", "reserved": "50", "available": "10"}, ...]`: one row per SKU, location and lot with stock, sorted by location, then SKU, then lot. `serials` lists the serials there, sorted. `reserved` counts reservations and picked stock there; `available` = on_hand − reserved. With `--at`, the stock as it stood then, without `reserved` and `available`.
- `available SKU --warehouse WH` → `{"sku": "...", "warehouse": "WH1", "available": "...", "incoming": "...", "backordered": "..."}`: `available` as above over the warehouse's `storage` locations; `incoming` is the open quantity of the product on the warehouse's POs; `backordered` is the quantity of the product on the warehouse's `confirmed`, `backordered` and `partially_shipped` orders that is neither reserved, picked nor shipped.

## 9. Transfers

- `transfer create SKU QTY --from WH1/LOC --to WH2/LOC [--lot LOT] [--serial S1,...]` sends unreserved stock from a `storage` location to a `storage` or `receiving` location of a different warehouse: a `transfer-out` movement (`to` null, `ref` the transfer id), valued as stock leaving the source warehouse (section 5). The stock is then in transit, in neither warehouse. → the `transfer show` object, status `in_transit`.
- `transfer receive TR` brings it into the destination: a `transfer-in` movement (`from` null, `ref` the transfer id) with the transfer's value. For `fifo` products, every slice the transfer consumed becomes a layer in the destination warehouse with the same unit cost and the same time and movement id as the layer it came from, so it keeps its age. For `average` products, it adds the transfer's value to V and its quantity to Q. Lots keep their expiry. Status `received`.
- `transfer cancel TR` returns an `in_transit` transfer to its source location: a `transfer-in` movement into it, with the transfer's value. For `fifo` products, the slices go back into the very layers they came from; for `average`, as for a receipt in the destination. Status `cancelled`.
- `transfer show TR` → `{"id": "TR-0001", "sku": "...", "qty": "...", "from": "WH1/A-01", "to": "WH2/RECV", "lot": null, "serials": [], "status": "in_transit", "value": "..."}`. `transfer list [--status S]` → those objects.

## 10. Returns

- `return create SO --line N --qty QTY --condition good|damaged [--to WH/LOC] [--lot LOT] [--serial S1,...]` records a customer return of a shipped line: QTY is at most the line's shipped quantity minus what was already returned. The return's unit cost is round4(the sum of the values of that line's `ship` movements / the line's shipped quantity). A `good` return needs `--to`, a `storage` location of the order's warehouse, and is a `return` movement (`from` null, `ref` the return id) with that unit cost and value round2(QTY × unit cost), costed like a receipt (section 5): for `fifo` products a new layer at the time of the return. A `damaged` return moves no stock and has value `"0.00"`. Lot-tracked products need a `--lot` shipped on that line; serial-tracked products need `--serial` with exactly QTY serials shipped on that line and not returned yet. The credit is round2(QTY × net / qty of the line). → `{"id": "RT-0001", "order": "SO-0001", "line": 1, "sku": "...", "qty": "...", "condition": "good", "to": "WH1/A-01", "lot": null, "serials": [], "unit_cost": "...", "value": "...", "credit": "..."}`.
- `return list [--order SO]` → those objects.

## 11. Reordering

- `reorder --warehouse WH` → `[{"sku": "...", "available": "...", "incoming": "...", "backordered": "...", "projected": "...", "min": "...", "max": "...", "suggest": "..."}, ...]` for products with a minimum whose projected quantity, available + incoming − backordered (section 8), is below the minimum. `suggest` is the maximum, or the minimum when there is no maximum, minus projected. `projected` may be negative. Sorted by SKU.

## 12. Import

- `import products FILE` reads a CSV file whose header is exactly `sku,name,unit,tracking,costing,min,max`. Empty `unit`, `tracking` or `costing` cells take the defaults; empty `min` or `max` cells leave them unset. Every row is checked by the rules of `product add`, and a SKU may appear only once in the file. If any row breaks a rule, nothing is imported, and stderr has one line per bad row, `error: row N: MESSAGE`, where N is the row's line number in the file (the header is line 1); exit code 2. Otherwise → `{"imported": 3}`.

## 13. Audit

- Every successful command that changes data appends one audit entry (plus `reservation.expire` entries, section 8). `audit list [--action ACTION] [--user NAME]` → `[{"seq": 1, "at": "2026-03-01T08:00:00Z", "user": "alice", "action": "init", "target": "EUR"}, ...]`, oldest first, with exactly those keys. Actions and targets: `init` (the currency), `user.add`, `user.role`, `user.disable` (the name), `product.add`, `product.edit` (the SKU), `import` (`products`), `warehouse.add` (the code), `location.add` (`WH/LOC`), `customer.add` (the name), `price.set` (`LIST/SKU`), `promo.add` (the code), `receive`, `move`, `adjust`, `scrap` (the movement id, as a string), `movement.void` (the id of the voided movement, as a string), `po.create`, `po.receive`, `po.close`, `so.create`, `so.confirm`, `so.allocate`, `so.pick`, `so.ship`, `so.cancel`, `transfer.create`, `transfer.receive`, `transfer.cancel`, `return.create` (the document id).

## 14. HTTP API

- `serve [--port N]` (default 8080) serves a JSON API on 127.0.0.1 until stopped. Each request runs as the user named in the `X-User` header, and at the time in the `X-Now` header (same format as `--now`; the real time without it); a missing, unknown or disabled user gets 401, a role too low gets 403. Request bodies are JSON objects; quantities, amounts and costs in them are strings (a JSON number is a 400). Errors return `{"error": "message"}`: 400 for user errors, 404 for an unknown path or object, and the codes below. A failed request changes nothing.
- `GET /products?search=TEXT&limit=N&after=SKU` → `{"items": [...], "next": "SKU" or null}`: up to N products (1 to 100, default 50) with SKU after `after`, sorted by SKU, filtered like `product list --search`; `next` is the last SKU returned when more products follow, else null.
- `GET /products/SKU` → the product object, with the header `ETag: "N"` (its version, in double quotes).
- `PATCH /products/SKU` with a body of any of `name`, `min`, `max` (null clears min or max) needs the header `If-Match: "N"`: without it, 428; when N isn't the current version, 412. → the updated product, with its new ETag.
- `POST /receipts` with `{"sku", "qty", "at", "cost", "lot"?, "expires"?, "serials"?: [...]}` → 201 and the movement. `POST /sales-orders` with `{"customer", "warehouse", "lines": [{"sku", "qty"}, ...]}` → 201 and the order. `POST /sales-orders/SO/confirm` with `{"hold"?: HOURS}` → 200 and the order. `GET /sales-orders/SO` → the order. `GET /stock?warehouse=WH&sku=SKU` → like `stock`. `GET /valuation?warehouse=WH` → like `valuation`.
- Any `POST` may carry an `Idempotency-Key` header. The first request with a key runs normally and its response (status and body) is kept, whatever the status. A later request with the same key, path and body gets that same response again and changes nothing; the same key with a different path or body gets 409. Keys are kept forever.
- The server handles requests in parallel. Whatever the timing of concurrent requests, stock is never reserved twice, never below zero, and every request is all-or-nothing.
