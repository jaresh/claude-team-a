## Assumptions
- A blank posting is stored with amount NULL; it is re-balanced by core.resolve_postings at each run, so the same balancing rule as txn add applies.
- Stored amounts are fmt(parse_money(...)), so "900" is stored as "900.00".
- Names are stripped; an empty name is a UserError ("name required"). A duplicate name is a UserError ("recurring exists: NAME").
- --every must be monthly, weekly or yearly; checked in recurring_add, not by argparse choices, so the API gets the same check.
- run iterates recurrings in creation order (rowid) and occurrences in date order; each occurrence is created with core.post_transaction, which checks the closed period. A closed-period hit raises UserError and core.run rolls back the whole run.
- Audit target for recurring.run is the until argument exactly as given. It is written only when created > 0.
- Occurrence k is computed from the original start (add_months(start, k) or start + 7k days), so a monthly Jan 31 start yields Feb 28, Mar 31, Apr 30, and never drifts.
- Start dates are not checked against closed periods on add (the spec only restricts postings made by run).
