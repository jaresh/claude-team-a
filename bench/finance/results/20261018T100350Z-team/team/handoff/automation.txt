Assumptions (also list these in README):
- rule add: the account must already exist (checked with ctx.account). Pattern is compiled with re.IGNORECASE and
  matched with re.search (anywhere in the description). An empty pattern is a user error.
- import: description is stripped; amount via parse_amount; a zero amount is accepted. Every row (including
  duplicates) is date-checked against closed periods before any write. The Uncategorized category accounts are
  created with ensure_account. Audit `import` is written on every success, even with 0 imported rows.
- import/recurring run/budget: the audit entry is also written on success when nothing changed (e.g. run with
  created 0). Spec says "changes data" but the plan says exactly one audit entry on success; this follows the plan.
- budget set: the account must be type expense; the amount must not be negative; amounts are in the book
  currency. report budget converts postings in other currencies at the month's last day (ctx.to_currency).
  Actual = postings to the account and its descendants in that month.
- recurring add: names are not unique. Postings are checked (accounts exist, at least 2, at most one missing
  amount, each currency balances unless that currency has the missing amount). Stored as JSON
  [{"account", "amount": "x.xx" or null}]. Output: {"id", "name", "every", "start"}.
- recurring run: occurrences are computed from the start with add_months/add_years (not iterated), weekly is
  start + 7k days. Any uncreated occurrence in a closed month makes the whole run fail, even one from long ago
  (spec-driven; it means a closed period with never-created occurrences blocks later runs).
  Created transactions are posted in date order, then recurring id order.
