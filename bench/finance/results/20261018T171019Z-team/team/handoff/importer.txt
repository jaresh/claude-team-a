Assumptions
- rule add: the pattern is compiled with re.IGNORECASE to validate it; the pattern is stored
  as given. An empty pattern is allowed (matches everything). Output: None (nothing printed).
- rule add checks ACCOUNT with core.account_type only; the account need not exist yet. The
  rule's account is created at import time (ensure_account, book currency) if missing.
- rule list: [{"pattern","account"}] by seq.
- import: the bank ACCOUNT must already exist (core.post raises "unknown account" otherwise).
  Not checked for type.
- Category: the first rule whose pattern matches the description (re.search, IGNORECASE);
  else Expenses:Uncategorized (amount < 0) or Income:Uncategorized (amount >= 0, so zero is
  Income). Uncategorized accounts are created in the book currency.
- Duplicate: an imports row with the same account, date, description and amount (amount
  compared as money string). Within one file the earlier row is already in imports when the
  later one is checked, so repeats are skipped naturally. A duplicate is skipped before the
  closed-period check, so re-importing a file whose rows are now in a closed month succeeds
  with those rows skipped; a new row in a closed month fails the whole import.
- Description and each field are stripped of surrounding whitespace. Dates via parse_date,
  amounts via parse_amount (at most two decimals). Column defaults 0/1/2; a missing column is
  a user error that names the row. Blank rows (all cells empty after strip) are skipped; the
  header (row 1 with --skip-header) is skipped. Row numbers count CSV records, header included.
- CSV is read as utf-8-sig (plain UTF-8 works; a BOM is dropped). Unreadable file: user error.
- Audit: exactly one `import` entry per successful command, even when 0 rows were imported.
- Edge: a rule pointing at an existing account in another currency makes the balanced check
  fail for that row (core.post sums per currency), so the import fails with a user error.
