Assumptions to list in README (my design decisions):
- A rule's account must exist when the rule is added (unknown account is a UserError).
- A rule pattern is a Python regex, matched case-insensitively; the first matching rule (by id) wins; with no match, the row goes to Expenses:Uncategorized (negative amount) or Income:Uncategorized (positive).
- A CSV row with a zero amount, a blank description, or a missing column makes the whole import fail, and nothing is posted.
- The category account must have the same currency as the import ACCOUNT; otherwise the import fails.
- Duplicate detection key: (account, date, description, amount). A repeat in the same file counts as a duplicate, so it is skipped.
- Closed periods are checked on every CSV row (including duplicates) and every due occurrence before anything is posted, so a closed period fails the whole import or run.
- Import and recurring run write one audit entry per command, even when nothing is created.
- Budget amounts are in the account's own currency and must be non-negative. The account must be of type expense. Setting a budget again for the same account and month replaces it.
- Budget actuals are the rolled-up balances for the month (child accounts included), converted into the budget account's currency at the month's end date.
- Recurring occurrences are computed from the start date each time (not chained). Monthly on the 31st gives Jan 31, Feb 28/29, Mar 31, Apr 30. Yearly from Feb 29 gives Feb 28 in non-leap years.
- A recurring start date in a closed period is rejected when the recurring transaction is added (dry run through Book.post).
- Recurring postings may have one missing amount, which balances the transaction, as in txn add.
- recurring run --until is inclusive.
